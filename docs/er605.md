# The router

TP-Link Omada ER605, **hardware v1.0**, firmware `1.3.2 Build 20251030`,
standalone mode with no controller. `10.100.100.1`.

This is a written record rather than a config file. The binary backup from
System Tools → Management → Backup & Restore lives in 1Password, not here: it
holds the admin password, it's opaque so you can't review or diff it, and TP-Link
backups are tied to a firmware version. This page is what you'd rebuild from.

## Before touching firmware

**This unit is hardware revision v1.0.** TP-Link firmware is hardware-specific and
the download site's default landing page serves **v2.x** images, covering hardware
v2.0 through v2.6. Flashing one of those onto a v1.0 board bricks it.

The correct page is `support.omadanetworks.com/en/download/firmware/er605/v1/`.
`1.3.2` is the newest for v1 hardware. Take a config backup first and flash from a
wired client, never over Wi-Fi.

## Ports

Network → WAN → WAN Mode, set to 2 WAN ports:

```
WAN        WAN        LAN       LAN       LAN
Telmex     Megacable  main Deco navi      ocarina (reserved)
```

Changing the number of WAN ports can discard your configuration. The page says so
and means it.

## The two lines

Both are Dynamic IP; neither does PPPoE at the router, since Telmex's PPPoE
terminates on the ONT.

| | Telmex | Megacable |
|---|---|---|
| Port | `WAN` | `WAN/LAN1` |
| Address | `192.168.30.200` | `192.168.1.2` |
| Gateway | `192.168.30.1` | `192.168.1.1` |
| DNS | `1.0.0.1`, `149.112.112.112` | `8.8.8.8`, `9.9.9.9` |
| Upstream | `500000` Kbps | `750000` Kbps |
| Downstream | `500000` Kbps | `750000` Kbps |
| MTU | `1492` | `1500` |

Both WANs also come up with IPv6 on Dynamic IP, which gets the router a global
address on each line and delegates no prefix to the LAN. Nothing behind the ER605
can use it. See [network.md](network.md).

Both have an empty Host Name, VLAN tagging disabled (the greyed defaults are 4094
on WAN and 4093 on WAN/LAN1), and "Get IP using Unicast DHCP" unchecked.

Telmex runs at MTU 1492 because its PPPoE session terminates on the ONT upstream
of the router. Matching it here avoids fragmentation. Megacable has no such
overhead, so 1500 is right.

> ### These bandwidth numbers are not decorative
>
> Load balancing is **bandwidth-weighted**, using exactly these two figures. Get
> one wrong and traffic silently stops using a line you're paying for.
>
> Found 2026-09-03: Telmex downstream was set to `50000` rather than `500000`, a
> missing zero. The router therefore treated a 500 Mbps line as 50 Mbps and gave it
> roughly 6% of download traffic instead of 40%. The visible symptom was every
> egress test coming back as Megacable, which looked like ordinary hash
> distribution and wasn't.
>
> If you ever change plans, update these. If traffic seems to favour one line
> oddly, check here first.

The per-WAN DNS split was set because Megacable appeared to route badly to
Cloudflare, measured at 55 ms against 11 ms to Google. **That measurement was
ICMP, and it's probably wrong.** By DNS query time, Cloudflare answers in 9 ms
from this network. Worth revisiting, though it costs nothing as it stands and
these servers are only used by the router itself now that Pi-hole handles clients.

## Load balancing

Transmission → Load Balancing → Basic Settings:

```
Enable Load Balancing                       on
Enable Application Optimized Routing        OFF   (see below)
Enable Bandwidth Based Balance Routing on   WAN, WAN/LAN1
```

Weighted 500:750 to match the two lines, using the Upstream/Downstream figures set
per WAN. **Link Backup deliberately empty**, so both lines carry traffic rather
than one sitting idle as a standby.

> ### Application Optimized Routing pins HTTPS to one line
>
> Measured 2026-09-03, after correcting the bandwidth figure:
>
> | Protocol | Result |
> |---|---|
> | HTTPS (443), 6 destinations, 2 source hosts | **12 of 12 out Megacable** |
> | HTTP (80), same destinations | **2 Telmex, 2 Megacable** |
>
> `ifconfig.me` and `icanhazip.com` go out Telmex on port 80 and Megacable on port
> 443. Same host, different port, different WAN. AOR is keying on the service and
> treating all HTTPS as one application.
>
> Since nearly all real traffic is HTTPS, **bandwidth-weighted balancing barely
> applies to anything you actually do.** Telmex carries the PS5 (by policy route),
> the `.61` probe, and plain HTTP. Megacable carries the rest.
>
> Nothing is broken and failover still works. But a 500 Mbps line is mostly idle.
>
> Turning AOR off would let HTTPS sessions distribute by weight. The cost is what
> AOR exists to prevent: your apparent public IP flipping between sessions, which
> triggers logouts, re-authentication and CAPTCHAs on sites that pin a session to
> an address. Banking and streaming are the usual casualties.
>
> **Left on**, for now. Revisit if Megacable's line becomes a bottleneck, or after
> bridge mode makes the two lines more symmetric.

## Online detection

Transmission → Load Balancing → Online Detection. This is how the router decides a
WAN is dead and fails over, so it matters more than its obscurity suggests.

| Port | Mode | Ping | DNS lookup |
|---|---|---|---|
| `WAN` (Telmex) | Manual | `1.1.1.1` | `8.8.8.8` |
| `WAN/LAN1` (Megacable) | Manual | `8.8.8.8` | `1.1.1.1` |

The targets are deliberately crossed. Each line watches a different provider, so
an outage at Cloudflare or Google can't make both WANs look dead simultaneously
and trigger a pointless failover in both directions.

Manual rather than Auto, so the targets are known rather than whatever the router
picks.

## Policy routes

Transmission → Routing → Policy Routing. All Service Type ALL, destination
`IPGROUP_ANY`, Priority mode.

| Name | Source | WAN | Why |
|---|---|---|---|
| `PlayStation` | `PlayStation` | `WAN` | Telmex is the only line that accepts inbound |
| `WANTestTelmex` | `WANTestTelmex` | `WAN` | forces monitoring out Telmex |
| `WANTestMega` | `WANTestMega` | `WAN/LAN1` | forces monitoring out Megacable |

**These only apply to TCP.** UDP and ICMP ignore them and fall back to load
balancing despite Service Type being ALL. See [gotchas.md](gotchas.md); it's the
reason the per-WAN monitors use HTTP.

If you rebuild the router, re-create these before trusting monitors 6 and 7 again.
Without them the checks come back green while measuring whichever line the
balancer picked.

## LAN and DHCP

```
LAN            10.100.100.1 / 255.255.255.0, VLAN 1
DHCP pool      10.100.100.100 - 10.100.100.199
Lease          120 minutes
Gateway        10.100.100.1
Primary DNS    10.100.100.53        (navi)
Secondary DNS  deliberately empty
```

The empty secondary is a decision, not an oversight. A public secondary makes ad
blocking leaky and unpredictable, because clients fall back to it whenever navi is
merely slow. See [decisions.md](decisions.md).

Everything below `.100` is outside the pool, so static addresses and reservations
can't collide with a lease.

## Address reservations

Network → LAN → Address Reservation.

| MAC | Address | Device |
|---|---|---|
| `08-BF-B8-A6-12-07` | `.20` | Windows PC |
| `80-60-B7-C6-19-AC` | `.30` | PS5 |
| `EC-74-8C-00-72-69` | `.31` | PS Portal |
| `88-A2-9E-1C-7D-08` | `.53` | navi |
| `1C-61-B4-F7-00-A1` | `.100` | main Deco |

**Leave "Export to IP-MAC Binding" unchecked on all of them.** It writes into the
anti-ARP-spoofing table and becomes a trap if strict mode is ever enabled.

The form sometimes rejects a valid address with "The IP address is not in the same
subnet as the IP address of LAN port." That's a stale client-side validator,
usually triggered by browser autofill. Hard-refresh and type the address by hand.

## IPv6

Both WANs have IPv6 connectivity from the ISPs (`2806:` prefixes visible on the
Status page). **It is not delegated to the LAN**, verified 2026-09-03: clients get
no routable v6 address, there's no v6 route off the network, and DHCP hands out a
single IPv4 nameserver.

That's why ad blocking is airtight. Pi-hole answers `AAAA` queries for blocked
domains with `::`, so both address families are covered, and there's no second
path to the internet that could route around it.

> **If IPv6 is ever enabled on the LAN, blocking leaks unless you also hand out
> `navi` as the IPv6 resolver.** Clients that get an ISP resolver over v6 will use
> it, quietly, for anything with an AAAA record. That covers most large sites.
> Enabling v6 without handing out a v6 DNS server is the specific mistake.

## UPnP

Services → UPnP. Enabled, LAN Interface `LAN`, Interface `WAN`, so it's scoped to
the **Telmex WAN only**. Narrowed from both WANs, since Megacable can't accept
inbound anyway.

Current portmap, which should be the only entry:

| Description | Protocol | Interface | Address | External | Internal |
|---|---|---|---|---|---|
| `10.100.100.30:9308 to 9308 (UDP)` | UDP | WAN | `10.100.100.30` | 9308 | 9308 |

That's the PS5 requesting a Remote Play mapping on demand. It appears and
disappears with use, so an empty list isn't a fault. **If UPnP ever gets disabled,
this mapping goes stale and Remote Play breaks in a way nobody attributes to the
router.**

## Verified empty, 2026-09-03

Checked so nobody has to wonder later, and so a stray rule appearing is
immediately suspicious:

Virtual Servers, Port Triggering, NAT-DMZ, Access Control and Link Backup are all
empty. Port Mirror is disabled (Port5 is preselected as the mirroring port and
Port1 as mirrored, but the feature is off, so it does nothing).

One-to-One NAT and ALG weren't checked. Neither is likely to hold anything, but
they're the two NAT tabs with no screenshot behind them.

**Nothing is port-forwarded, which is the standing rule.** Telmex's ONT DMZs
everything to the ER605's WAN, so that interface does see the open internet; with
no forwards and no DMZ configured here, it all gets dropped.

**Attack Defense is entirely disabled, deliberately.** Those are legacy DoS
filters, and with zero forwarded ports the inbound surface is already nothing.
Enabling flood defense at stock thresholds mostly buys intermittent dropped
traffic that's painful to diagnose. "Block Ping from WAN" is the only one worth
considering, and it would break the cross-ISP monitoring idea in
[future-plans.md](future-plans.md).

## Clock

UTC-06:00, corrected 2026-09-03. It had been on **(UTC-08:00) Pacific**, leaving
the router's clock two hours behind everything else in the house. Nothing breaks,
but the day you correlate an ER605 log entry against an Uptime Kuma alert the
timestamps won't line up, and you'll misread cause and effect.

DST stays off. Mexico abolished it in 2022.

Time Config is "Get automatically from the Internet", with both NTP server fields
left at `0.0.0.0`, meaning the firmware's own defaults.

## Reaching the UI

`router.lan` and `gate.lan` resolve to **navi**, not to the router, and Caddy
proxies them through to `https://10.100.100.1`.

That's not decoration. The ER605 answers on 443 with a certificate TP-Link
generated in 2018, so any browser that auto-upgrades to HTTPS (most of them now)
lands on a full-page security warning every single time. Behind the proxy the
browser sees a certificate from navi's own CA instead, and it just loads.

Caddy talks to the router over **plain HTTP**, not its HTTPS. Proxying to 443
fails with `remote error: tls: handshake failure`: the ER605's TLS stack is from
2018 and only offers cipher suites Go's client refuses. `curl` connects because
it's more permissive, which makes this look like a Caddy bug rather than an old
appliance. Caddy's http transport has no minimum-version setting for upstreams, so
there's no way to negotiate down.

That hop is therefore cleartext. It's one switched hop on the same wire, and it's
what already happened whenever you browsed to `http://10.100.100.1`. The
browser-to-navi half is now encrypted, so the plaintext segment got shorter, not
longer.

**`https://10.100.100.1` still works directly and always will.** That's the path
to use when navi or Caddy is the thing that's broken, and it's why the address is
worth remembering even though the alias exists.

## Two things that will catch you

**The web UI locks out after 10 failed logins.** Remember it before guessing at
the password or scripting anything against it.

**Adopting this into an Omada Software Controller does not migrate its
configuration.** The device is reprovisioned and everything on this page has to be
re-created inside the controller. That config took a full evening to get right and
it works. Either budget the time to rebuild it, or skip the controller entirely.
Uptime Kuma already covers the original complaint, which was not noticing a dead
ISP, without touching a working router.
